# Как сдавать домашние задания

Полная последовательность действий для одного домашнего задания.
Повторяйте её для каждого ДЗ, меняя номер ветки: `hw-02`, `hw-03`, …,
`hw-12`.

Порядок разбирается вживую на занятии 2 «Работа с Git», и **начинается он
с ДЗ-2**. В ДЗ-1 ветка и pull request не нужны: там достаточно создать
репозиторий из шаблона, склонировать его и убедиться, что программа
запускается. Требовать порядок, который ещё не объясняли, было бы странно.

Этот файл — чтобы не держать последовательность в голове и возвращаться к
ней перед каждой сдачей, пока она не станет привычной.

## Шаг 1. Обновите локальную `main`

```
git checkout main
git pull --ff-only
```

Делайте это перед началом каждого ДЗ, даже если кажется, что в `main`
ничего не менялось: если предыдущий pull request уже слит, локальная
`main` должна об этом узнать.

Флаг `--ff-only` означает «только перемотка, без слияния». Если история
почему-то разошлась, команда откажется работать и покажет ошибку — это
повод разобраться, а не игнорировать.

## Шаг 2. Создайте ветку от `main`

```
git checkout -b hw-03
```

Номер — текущего задания. **Ветка создаётся от актуальной `main`, а не от
предыдущей ветки с предыдущим номером.** Иначе в pull request попадут
изменения прошлого ДЗ, и ментору будет непонятно, что именно вы сдаёте.

## Шаг 3. Напишите код и проверьте локально

Перед отправкой прогоните проверки у себя. До занятия 3 достаточно двух
команд, для которых кроме Go ничего не нужно:

```
go build ./...
go test ./...
```

После занятия 3, когда поставите Task или make, то же самое делается одной
командой — `task check` или `make check`. Она добавляет форматирование,
`go vet` и линтер, то есть ровно то, что запустит автопроверка после
отправки: увидеть ошибку локально дешевле, чем в красном pull request.

## Шаг 4. Зафиксируйте изменения коммитом

```
git add .
git commit -m "ДЗ-3: вывод списка задач и фильтрация по статусу"
```

Сообщение пишите так, чтобы по нему было понятно, что сделано. Через месяц
`git log` из десяти строк «fix», «fix2», «правки» не скажет вам ничего.

Несколько коммитов по ходу работы — это нормально и даже полезно: видно,
что и когда менялось.

## Шаг 5. Отправьте ветку

```
git push -u origin hw-03
```

Флаг `-u` нужен один раз для ветки: он связывает локальную ветку с
удалённой, дальше достаточно `git push`.

## Шаг 6. Создайте pull request

Откройте репозиторий на GitHub — там появится предложение создать pull
request из только что отправленной ветки. Base-веткой должна быть `main`,
сравниваемой — ваша `hw-NN`.

Заполните шаблон: номер задания, что сделано, как запустить. В шаблоне есть
**чек-лист самопроверки** — пройдите его перед тем, как звать ментора. Он
ловит то, из-за чего работы возвращают чаще всего.

## Шаг 7. Дождитесь автопроверки

После создания pull request автоматически запускается проверка. Результат
виден на вкладке **Checks** на странице pull request. Настраивать ничего не
нужно, она одинакова для всех заданий.

**Если проверка красная:** откройте лог упавшего шага, найдите, на чём она
споткнулась, исправьте локально и сделайте новый коммит в ту же ветку.
Pull request и проверка обновятся сами — открывать всё заново не нужно.

Красная проверка — не повод для паники и не отметка о качестве работы. Чаще
всего это забытый `gofmt` или неиспользованная переменная.

## Шаг 8. Получите ревью и внесите правки

Ментор оставляет комментарии в pull request. Правки вносите новыми
коммитами в ту же ветку — история обсуждения при этом сохраняется, и видно,
что на что вы поменяли.

## Шаг 9. Слейте pull request

После подтверждения ментора слейте pull request в `main` через
веб-интерфейс GitHub. Ветку после слияния можно удалить — GitHub предложит
это сам.

Следующее ДЗ начинайте с шага 1: обновить `main`, чтобы в ней оказался
только что слитый код.

## Пять ошибок, из-за которых работы возвращают чаще всего

**Работа прямо в `main`.** Тогда либо не из чего делать pull request, либо
портится локальная `main`. Проверяйте текущую ветку командой `git status`
перед тем, как начать писать код.

**Ветка `hw-04`, созданная от `hw-03`.** В pull request попадут изменения
прошлого задания. Лечится шагом 1: всегда начинать с обновления `main`.

**Закоммиченный бинарник или файл IDE.** Раздувает историю и мешает читать
изменения. Файл `.gitignore` в шаблоне уже исключает типичные артефакты —
не удаляйте из него строки только потому, что «мешают» добавить нужный
файл.

**Коммит с сообщением «fix».** Смотрите шаг 4.

**Функционал прошлых ДЗ потерялся.** Проект накапливается: то, что работало
в ДЗ-5, должно работать и в ДЗ-9. Если при рефакторинге что-то отвалилось,
это заметят.

## Если застряли

Пишите в учебный чат. Это не «сдаться», а обычный рабочий ход: половина
вопросов первой недели — про установку и Git, и почти все решаются за пару
сообщений.
