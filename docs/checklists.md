# Что проверяется в домашних заданиях

Списки того, что смотрит проверяющий. Ничего нового по сравнению с
условием задания здесь нет: **у каждого пункта в скобках указано, откуда
он взят**, и источников ровно три — текст задания, общие требования к
сдаче ДЗ и этот репозиторий-шаблон.

Смысл публикации в том, чтобы вы видели список до сдачи, а не узнавали о
нём из комментария ментора.

## Как этим пользоваться

Пройдите список перед тем, как звать ментора в pull request. Пункт, который
не выполнен, — это возврат работы на доработку, и лучше увидеть его самому.

**Читайте только два раздела: общий и текущего задания.** Файл длинный,
потому что покрывает весь курс; просматривать будущие ДЗ сейчас не нужно и
незачем.

Списки готовы для ДЗ-3…ДЗ-12 — всех заданий сквозного проекта. У ДЗ-1 и
ДЗ-2 своих списков нет: они про настройку окружения и первый репозиторий,
там проверяется наличие, а не устройство кода.

Порядок сдачи — в [submitting.md](submitting.md).

## Что проверяется в каждом задании

Эти пункты одинаковы для всех заданий сквозного проекта — с ДЗ-3 по ДЗ-12.
Работа не принимается, если не выполнен хотя бы один.

К ДЗ-1 и ДЗ-2 они не относятся: там студент настраивает окружение и заводит
репозиторий, и проверяется другое — критерии этих заданий перечислены в них
самих.

- [ ] Проект собирается и запускается: `go build ./...` без ошибок,
      `go run ./cmd/todo` стартует. *(общие требования, п. 4)*
- [ ] Автоматическая проверка pull request зелёная. Она прогоняет
      форматирование, `go vet`, сборку, линтер и тесты — ровно то, что
      перечислено в чек-листе самопроверки в описании pull request.
      *(шаблон курса)*
- [ ] Работа сдана в отдельной ветке `hw-NN` через pull request.
      *(общие требования, п. 2)*
- [ ] В корне репозитория есть `README.md` с описанием проекта.
      *(общие требования, п. 3)*
- [ ] В pull request нет собранных бинарников, файлов IDE и временных
      файлов. *(шаблон курса: `.gitignore` и чек-лист pull request)*
- [ ] Функционал предыдущих ДЗ на месте и работает: проект накапливает
      возможности, а не переписывается с нуля. *(общие требования, п. 5)*

Всё, что не перечислено здесь и в списке к конкретному заданию, работу не
блокирует. Такие вещи преподаватель может разобрать с вами на ревью —
это разговор о том, как код будет выглядеть дальше по курсу, а не
основание вернуть задание на доработку.

### Оговорка про имя пакета

Если вы положите функции проверки в пакет с именем `validate`, линтер в
автоматической проверке скажет, что имя `validate.ValidateTask` «заикается»,
и предложит переименовать функцию. Переименовывать её не нужно — имя задано
условием. Назовите пакет существительным: `validation` вместо `validate`, и
замечание уйдёт. Заглушать линтер через `//nolint` не надо: заглушка
останется в коде и перейдёт в следующие задания.

### Оговорка про JSON-теги

Пункты 3 и 4 задания вместе не выполняются: `go vet` отвергает тег на
приватном поле сообщением `struct field has json tag but is not exported`, а
чистый `go vet` нужен для зелёной автоматической проверки. Выберите одно:

- **приватные поля без тегов** — этого требует критерий оценки, и так
  сделано в разборе задания;
- **экспортируемые поля с тегами** — тоже принимается, но инкапсуляции в
  таком варианте нет: снаружи пакета можно записать в поле напрямую, минуя
  конструктор и проверки.

Работа не возвращается ни в одном из двух случаев — противоречие в самом
условии, а не в вашем решении. Теги до занятия 22 всё равно ничего не
делают: они понадобятся в ДЗ-9 «Сохранение в JSON/CSV».

### Оговорка про типы в хранилище

Пункт 2 предлагает слайс `[]Task` вместе с `map[int]*Task`. Написанная в
лоб, эта пара разъезжается: указатель в мапе смотрит на элемент массива под
слайсом, а `append` при нехватке ёмкости переносит элементы в новый массив —
и с этого момента слайс и мапа держат разные копии одних и тех же задач.
Удаление добавляет своё: сдвиг элементов сбивает указатели.

Правило приёмки такое: **сам выбор `[]Task` допустим, но если после
добавления или удаления данные расходятся — CRUD не работает, и работа
возвращается**.

Проверяется это просто: добавьте задач больше, чем помещалось изначально,
потом измените одну через мапу и прочитайте её через слайс. Значения обязаны
совпасть. То же после удаления из середины.

Какую пару структур взять, чтобы этого не случилось, решаете вы. Отступление
от буквы пункта 2 ошибкой не считается: критерий — работающий CRUD, а не
конкретные типы.

### Оговорка про типы в каналах

Условие называет каналы `jobs chan Task` и `results chan Task`. Если ваш
тип `Task` сделан по ДЗ-5 — приватные поля, методы на указателе, — то
значение `Task`, приехавшее по каналу, изменить нельзя: у значения нет
метода `SetStatus`. Берите `chan *Task`, это не отступление от задания.

Отдельная вещь, которую условие не проговаривает, но которая важнее типа:
**одну и ту же задачу не должны одновременно менять воркер и главная
горутина.** Если это происходит, у вас гонка данных: программа работает, но
иногда показывает не то, что есть на самом деле. Ни компилятор, ни `go vet`
про неё не скажут.

Проверяется прогоном с детектором гонок:

```
go run -race ./cmd/todo
```

Пройдите обычный сценарий — добавить задачи, запустить обработку, вывести
список. Если детектор молчит, пункт выполнен; если печатает `DATA RACE`,
читайте, какие две горутины и по какому адресу столкнулись, — там и ответ.
Как устроить обмен без гонки, решаете вы: занятие 16 даёт для этого каналы.

Мьютекса на этом задании ещё нет: он появится на занятии 17, уже после
сдачи. Ответ занятия 16 — другой по природе: не делить память между
горутинами, а передавать данные через канал.

### Оговорка про `select` по трём каналам

Пункт 4 читается как требование одного `select` сразу по трём каналам —
`events`, `results` и `done`. Собрать такой `select` в этом задании можно
только с веткой, которая никогда не срабатывает: `events` читает
слушатель, `results` — та горутина, которая кладёт результаты в
хранилище, а закрывает `done` она же.

Достаточно одного `select`, который ждёт нескольких каналов и делает
осмысленную работу. Обычные места — слушатель событий (`events` и `done`)
и воркер (`jobs` и `done`). Работа с тремя каналами в одном `select` тоже
принимается.

### Как проверить завершение по сигналу

Конвейером это не проверяется: сигнал надо послать работающему процессу.
Запустите программу, выберите пункт обработки задач и нажмите Ctrl+C, не
дожидаясь конца обработки. Программа обязана отчитаться и выйти сама.

**Необязательно, на приёмку не влияет.** Есть второй случай: Ctrl+C, пока
программа ждёт пункт меню. Если она завершается только после следующего
Enter — сигнал перехвачен, но главная горутина всё ещё стоит на чтении
ввода. Отмена контекста чтение из `os.Stdin` не прерывает; чтобы реагировать
и здесь, ввод читают отдельной горутиной, отдающей строки в канал, а в меню
ждут `select`-ом сразу двух вещей: строки и отмены.

Это улучшение, а не требование: условие такого не просит, и работа без него
принимается. Заодно имейте в виду, что до конца эту горутину всё равно не
убрать — разбудить `Scan`, ждущий строку, нечем ни в каком варианте. Она
останется висеть до выхода из процесса, и это нормально: так сделано и в
разборе задания.

### Оговорка про срок на задачу

В условии стоит «например, 5 секунд». Имитация работы из ДЗ-7 занимает
1–3 секунды, поэтому при пяти секундах таймаут не сработает никогда, и
проверить эту ветку запуском не получится. Возьмите срок меньше — двух
секунд достаточно, чтобы часть задач в него не уложилась. Оба варианта
принимаются.

### Оговорка про «дождаться завершения текущих задач»

Пункт 1 просит дождаться завершения текущих задач, а пункт 2 — ограничить
задачу контекстом, порождённым от корневого. Одно спорит с другим: такой
контекст при сигнале отменяется, и текущая задача прерывается, а не
доводится до конца.

Принимаются оба прочтения:

- задача прерывается, но программа дожидается воркеров и отчитывается по
  каждой начатой задаче — прерванная попадает в статистику отдельной
  строкой;
- начатая задача доводится до конца, и только потом программа выходит.

Чего быть не должно ни в одном случае: задачи, о которой не пришло
никакого отчёта, и процесса, убитого сигналом на середине.

- [ ] Формат хранения выбирается флагом командной строки или переменной

- [ ] Файлы закрываются через `defer`. *(задание, п. 4)*
- [ ] Ошибки чтения и записи обрабатываются, а не игнорируются. *(задание,

      критерий «Данные сохраняются при graceful shutdown»)*

### Как проверить себя

Одного запуска мало: главное в этом задании — что данные переживают
перезапуск. Запустите программу, добавьте задачу, выйдите, запустите снова и
посмотрите на список. Затем откройте сам файл и посмотрите, что в нём.

Строка `{}` или `[{},{}]` в файле означает, что задачи не сохранились. Это
самая частая ошибка задания, и ошибки при ней не будет ни одной — см.
оговорку ниже.

Отдельно проверьте удаление: удалите задачу, выйдите, запустите снова.
Забывают именно его — задача пропадает из памяти и возвращается после
перезапуска.

### Оговорка про приватные поля и JSON

Тип `Task` из ДЗ-5 имеет только приватные поля, а в JSON попадают только
экспортируемые: `json.Marshal` вернёт `{}` и никакой ошибки. Тег этого не
меняет — тег на приватном поле вообще отвергает `go vet`.

Выходов два, и оба принимаются:

- **сделать поля экспортируемыми и повесить теги на них** — просто и
  работает сразу, цена — инкапсуляция, ради которой поля делались
  приватными;
- **оставить поля приватными и написать `MarshalJSON` и `UnmarshalJSON`** —
  кода больше, зато проверки остаются на месте, а в `UnmarshalJSON`
  появляется удобное место для проверки данных, пришедших из файла.

Работа не возвращается ни в одном из двух случаев: критерии говорят про
сохранение и загрузку, а не про устройство типа. Быть готовым объяснить
выбор на код-ревью стоит.

С CSV этого вопроса не возникает: там вы сами составляете строку таблицы из
значений полей, и приватность внутри своего пакета ничему не мешает.

### Оговорка про время в CSV

Формат времени условие не задаёт, и превращать `time.Time` в строку вам.
Естественная попытка — напечатать время глаголом `%v` — даёт строку вида
`2026-01-15 08:30:00 +0000 UTC`, которую обратно не разбирает ничто.
Сохранение при этом выглядит выполненным: файл создан, колонки на месте.
Ломается загрузка, и заметить это можно только вторым запуском.

Надёжный вариант — `t.Format(time.RFC3339)` при записи и
`time.Parse(time.RFC3339, ...)` при чтении. Свой формат тоже принимается,
если задачи после перезапуска возвращаются: проверяется исход, а не способ.
В JSON этой заботы нет — `time.Time` умеет себя сам.

### Про файл с задачами и git

Файл, который программа переписывает при каждом изменении, в репозитории не
нужен: он меняется от каждого запуска и в pull request только мешает.
Допишите его в `.gitignore` — или кладите данные в отдельный каталог и
игнорируйте каталог целиком.

### Как проверить себя

Поднимите базу, запустите программу с `--storage=postgres`, добавьте задачу,

docker compose exec postgres psql -U otus -d otus -c "SELECT id, title, status FROM tasks ORDER BY id;"

Пройдите так по всем шести операциям: после каждой смотрите в таблицу. Это и

Отдельно проверьте два случая, которых на первом запуске не видно.

Остановите программу, запустите снова и добавьте задачу. Если она добавилась
и видна в таблице — пункт выполнен; если получили ошибку, разберитесь,

что задачи нет. Для базы такой запрос ошибкой не является, поэтому проверьте

посмотрите, что программа ответит.

`--storage=json` и `--storage=memory` обязаны запускаться так же, как

### Оговорка про имя типа хранилища

Условие называет тип `PostgresStorage`. Пакет для работы с базой иначе как
`postgres` не назовёшь, а в нём это имя читается как
`postgres.PostgresStorage` — слово повторяется дважды. `golangci-lint`
отвечает на это замечанием:

```
type name will be used as postgres.PostgresStorage by other packages,
and that stutters; consider calling this Storage (revive)
```

**Принимаются оба имени** — и `PostgresStorage`, и `Storage`. Требование не
ослаблено: проверяется, что есть отдельный пакет для работы с PostgreSQL и
тип хранилища в нём. Просто условие ДЗ и правила именования в Go здесь
расходятся между собой, и выбор любого из двух имён — не ваша ошибка.

Если вы оставили имя из условия и получили это замечание, красная
автопроверка по этой и только по этой причине работу не блокирует. Ставить
`//nolint` не надо: заглушка останется в коде и разойдётся по следующим ДЗ.
Имя в Go читается вместе с именем пакета, и `postgres.Storage` — это уже
«хранилище PostgreSQL», добавлять к нему слово `Postgres` нечего. Тот же
случай был в ДЗ-4 с `validate.ValidateTask`.

### Оговорка про имя файла Compose

Условие говорит `docker-compose.yml`. Программа `docker-compose` через дефис
— инструмент предыдущего поколения, и в текущих установках Docker её может
не быть: Compose встроен в сам `docker` и вызывается командой из двух слов,
`docker compose`, а имя файла по умолчанию у него `compose.yaml`. Старое имя
он читает тоже.

**Принимаются оба имени.** Если вы получили `docker-compose: command not
found`, дело не в вашей работе: пользуйтесь `docker compose` и называйте
файл как удобно.

### Оговорка про строку подключения

Адрес базы, имя пользователя и пароль в коде не пишут: они приходят из флага
или переменной окружения. Значение по умолчанию, совпадающее с вашим
Compose, — это нормально и удобно; зашитая намертво строка, которую нельзя
поменять снаружи, — нет. Флаги и переменные окружения разбирались на
занятии 21.

### Оговорка про тесты и Docker

Автоматическая проверка pull request поднятой базы не имеет. Тест, который
подключается к PostgreSQL безусловно, сделает её красной — и это будет
выглядеть как поломка вашей работы.

Тестов задание не требует вовсе. Если вы их пишете, есть два рабочих
способа: подставлять в хранилище не `*pgxpool.Pool` и не `*sql.DB`, а
маленький интерфейс, который в тесте заменяется своей структурой (так
сделаны упражнения занятия 23), либо пропускать тест через `t.Skip`, когда
базы нет, сообщением, называющим команду её запуска.

### Оговорка про дополнительную часть

Миграции (goose или golang-migrate) и индекс на `status` названы в условии
дополнительными. На приёмку они не влияют: работа без них принимается.

## В ДЗ-11 «REST API для задач»

Кроме общих требований к сдаче ДЗ:

- [ ] Сервер написан на стандартной библиотеке: ни `gin`, ни `chi`, ни
      `echo`, ни `gorilla/mux` в `go.mod` нет. *(задание, п. 1; критерий
      «REST API реализован на чистом `net/http`»)*
- [ ] Есть все пять маршрутов: `POST /api/tasks`, `GET /api/tasks`,
      `GET /api/tasks/{id}`, `PUT /api/tasks/{id}`,
      `DELETE /api/tasks/{id}`. *(задание, п. 1; критерий «Все
      CRUD-операции доступны через HTTP»)*
- [ ] Создание отвечает 201, получение и обновление — 200. *(задание, п. 2;
      критерий «Корректные HTTP-коды ответов»)*
- [ ] Негодные данные дают 400: пустое название, недопустимый статус,
      неразобранное тело. *(задание, п. 2)*
- [ ] Несуществующая задача даёт 404 — не 200 с пустым телом и не 500.
      *(задание, п. 2)*
- [ ] Ответы приходят в JSON, и у всех одна структура с полями `data` и
      `error`. *(задание, п. 3; критерий «Ответы в формате JSON»)*
- [ ] Фильтр по статусу работает: `GET /api/tasks?status=<статус>`
      возвращает только задачи с этим статусом. *(задание, п. 4)*
- [ ] В README работы написано, как запустить сервер и какие адреса он
      слушает. *(общие требования, п. 3)*

### Как проверить себя

Поднимите сервер и пройдите все пять маршрутов подряд — так же, как это
будет делать проверяющий. Флаг `-i` показывает код ответа, без него его не
видно:

```
curl -i -X POST http://127.0.0.1:8080/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"купить хлеб","description":"в булочной у дома"}'

curl -i http://127.0.0.1:8080/api/tasks
curl -i http://127.0.0.1:8080/api/tasks/1
curl -i -X PUT http://127.0.0.1:8080/api/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"title":"купить хлеб","description":"в булочной","status":"завершена"}'
curl -i -X DELETE http://127.0.0.1:8080/api/tasks/1
```

Отдельно пройдите то, на чём чаще всего спотыкаются:

- **пустое название** — ожидается 400, а не 201 с пустой задачей;
- **несуществующий номер** — `curl -i http://127.0.0.1:8080/api/tasks/999999`
  ожидается 404;
- **не число вместо номера** — `/api/tasks/abc` тоже не должно давать 500;
- **фильтр** — заведите задачи с разными статусами и убедитесь, что
  выборка возвращает только нужные.

И обязательно проверьте, что **не сломалось прошлое**: выбор хранилища
конфигурацией из ДЗ-10, сохранение из ДЗ-9, проверка данных из ДЗ-4 должны
работать как раньше. Проект накапливается, а не заменяется.

### Оговорка про значения статусов

Пункт 4 приводит пример `GET /api/tasks?status=done`, а статусы в проекте с
ДЗ-3 русские: «новая», «в работе», «завершена». Значения `done` в проекте
нет.

**Принимаются оба решения:** фильтр по русским статусам проекта (тогда
`?status=done` возвращает пустой список или 400 — это не ошибка) либо
английские коды статусов, если вы переведёте на них весь проект. Чего быть
не должно — двух наборов значений одновременно, когда API говорит на одном
языке, а файл и база на другом.

### Оговорка про код ответа на удаление

Условие не называет код для `DELETE`. Принимается и 200 с телом, и 204 без
тела — оба варианта общеприняты. Важно, что удаление несуществующей задачи
даёт 404, а не молчаливый успех.

### Оговорка про меню из прошлых заданий

Условие не говорит, что делать с консольным меню, которое вы вели с ДЗ-3.
Дело в том, что меню читает ввод и заканчивается вместе с ним, а сервер
обязан работать, пока его не остановят: запустить оба сразу в одной
программе не получится.

**Принимаются любые из трёх решений:** режим работы выбирается
конфигурацией (меню или сервер); меню убрано, остался сервер; меню
осталось, а сервер поднимается отдельной командой. Требование одно —
функционал прошлых ДЗ должен быть достижим, а как именно, решаете вы.

### Про пункт 5: корректное завершение

Пункт 5 требует graceful shutdown, но в критериях оценки его нет, и на
занятии 26 эта тема разбирается одним примером в конце. **Поэтому работа
за него не возвращается.**

Сделать его всё же стоит: сервер, который умеет останавливаться, не бросая
начатые запросы, — это то, с чего начинается любой рабочий сервис, и на
код-ревью про него спросят. Если делаете, проверьте две вещи, которые чаще
всего выходят неверно: срок на остановку не должен браться из контекста,
который уже отменён сигналом, и хранилище закрывается после остановки
сервера, а не до.

      случая пункта 4: создание 201, ошибка проверки данных 400,

      критерий «Написаны тесты HTTP-обработчиков через httptest»)*
- [ ] `github.com/stretchr/testify` есть в `go.mod` и действительно
      используется в тестах. *(задание, п. 3; критерий «Используется
      библиотека testify»)*
- [ ] Покрытие бизнес-логики не меньше 60% по правилу, объявленному
      преподавателем. *(задание, п. 5; критерий «Покрытие бизнес-логики не
      менее 60%»)*
- [ ] Тесты действительно проверяют поведение, а не только исполняют код.

      требуемого случая не покрывает)*

### Как измерить покрытие

Условие называет команду `go test -cover`, но она печатает число по каждому
пакету отдельно, а общего не даёт. Что считать бизнес-логикой, условие тоже
не уточняет, поэтому **правило объявляет преподаватель до сдачи** — уточните
его, если не прозвучало.

Обычно в счёт идут пакеты с проверкой данных, с хранилищем и с
HTTP-обработчиками, а `cmd`, разбор конфигурации и код доступа к базе — нет.
Команда:

```
go test -coverprofile cover.out ./internal/validation/ ./internal/storage/ ./internal/api/
go tool cover -func cover.out | tail -1
```

То же в PowerShell на Windows:

```
go test -coverprofile cover.out ./internal/validation/ ./internal/storage/ ./internal/api/
go tool cover -func cover.out | Select-Object -Last 1
```

Значение флага здесь отделено **пробелом**, а не знаком равенства: привычная
форма `-coverprofile=cover.out` в PowerShell не работает.

Файлы `cover.out` и `coverage.html` — артефакты, в коммит они попадать не
должны; `.gitignore` шаблона их уже исключает.

### Как проверить, что тесты не пустые

Покрытие показывает, что строка исполнилась, — и только. Тест без единой
проверки даёт покрытие и всегда зелёный, поэтому и стоит отдельный пункт
про то, что тесты замечают неверное поведение.

Проверить себя можно так: **сломайте свой код и посмотрите, покраснели ли
тесты.** Возьмите два-три места, которые вы объявили покрытыми, — например,
уберите одно условие из проверки данных или строку, удаляющую задачу из
хранилища, — запустите тесты и верните код обратно.

Если после поломки тесты остались зелёными, соответствующий случай не
покрыт, сколько бы тестов ни было написано.

### Оговорка про то, какое хранилище покрывать

К этому заданию у проекта несколько реализаций хранилища: память с ДЗ-6,
файл с ДЗ-9, PostgreSQL с ДЗ-10. Пункт 2 говорит про «хранилище» в
единственном числе и не уточняет, какое.

**Принимается любое из трёх:** тесты только для хранилища в памяти
(минимум, которого требует буквальное чтение пункта 2), отдельные тесты
для каждой реализации или один табличный тест, прогоняемый по нескольким
реализациям сразу.

Чего быть не должно — теста PostgreSQL, который в общем прогоне требует
поднятой базы. Автопроверка pull request Docker не поднимает, и работа
станет красной не по вашей вине. Такой тест обязан пропускать себя без
переменной окружения — приём знаком с ДЗ-10.

### Оговорка про смешанный стиль

Пункт 3 требует использовать `testify`, но не требует переписать на него
все тесты сразу. Если часть тестов написана на стандартной библиотеке, а
часть на `testify`, работа принимается: критерий говорит про использование
библиотеки, а не про единообразие.

### Чего в требованиях нет

Ни конкретного числа тестов, ни `t.Parallel`, ни фаззинга, ни тестов `cmd`,
ни покрытия выше 60%, ни обязательного `go test -race`. Всё это полезно и
обсуждается на код-ревью, но работу за отсутствие не возвращают.
